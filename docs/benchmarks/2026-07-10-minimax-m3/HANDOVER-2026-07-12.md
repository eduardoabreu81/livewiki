## Critical correction to the clean v9 executor report

The final report attributed both failed tasks to provider `abort`, but the
persisted checkpoint shows a mixed failure sequence:

| Module | Attempt | Input | Output | Normalized stop | Raw reason |
|---|---:|---:|---:|---|---|
| `core-src-02` | 1 | 18,586 | 4,257 | `complete` | `stop` |
| `core-src-03` | 1 | 17,449 | 4,140 | `complete` | `stop` |
| `core-src-03` | 2 | 20,195 | 3,043 | `complete` | `stop` |
| `core-src-03` | 3 | 28,272 | 769 | `incomplete` | `abort` |
| `core-src-04` | 1 | 19,441 | 721 | `incomplete` | `abort` |
| `core-src-04` | 2 | 19,940 | 4,821 | `complete` | `stop` |
| `core-src-04` | 3 | 28,989 | 652 | `incomplete` | `abort` |

Consequences:

1. MiniMax returned three undocumented `abort` completions. Rejecting them was
   correct. MiniMax documents normal OpenAI-compatible finish reasons as
   `stop`, `length`, and `tool_calls`; `abort` is not a normal documented text
   completion. Reference: [MiniMax OpenAI-compatible API](https://platform.minimax.io/docs/api-reference/text-chat-openai).
2. Three responses for the failed modules ended normally with `stop` and were
   still rejected by normalization, artifact validation, or verify.
3. The exact rejection codes for those completed responses are no longer
   recoverable from v9 evidence.
4. The circuit breaker correctly stopped after one success and two task
   failures (>50% after at least three attempted stage-4 tasks).

Do not describe v9 as merely a MiniMax abort incident. It is both provider
incompletion and completed-candidate validation failure.

## Confirmed product observability defect

The bounded stage-4 loop keeps only mutable `priorCandidate` and `priorErrors`.
Each attempt replaces `priorErrors`. `UsageAttempt` persists tokens and stop
reasons, but not the normalization/validation/verify outcome for that attempt.

When repair is exhausted, the final message uses only `priorErrors[0]` from the
last attempt and reports `priorErrors.length` as "Total errors recorded". In
v9 this produced a misleading terminal report containing only
`incomplete_generation / abort`, hiding the completed-but-invalid attempts.

No raw candidate content was retained by the product or token proxy, so the
missing validation codes cannot be reconstructed after the fact.

## Plausible contributing factor — not yet proven root cause

Repair prompts grew substantially because they include source context, the
closed list, structured errors, and up to 16,000 characters of the prior
candidate:

- `core-src-03`: 17,449 input tokens initially, 28,272 on the final repair.
- `core-src-04`: 19,441 initially, 28,989 on the final repair.

Both final large repair calls returned short `abort` outputs. This correlation
suggests repair amplification may contribute, but it does not explain the
completed invalid responses and is not sufficient evidence for changing caps
or splitting rules.

## Immediate next work — local only, no paid API

### 1. Persist per-attempt diagnostics

Add an append-only diagnostic history to the stage-4 task checkpoint. A safe
entry should contain:

- global attempt number;
- normalized and raw stop reason;
- outcome category: `llm_error`, `incomplete_generation`,
  `normalization_failed`, `artifact_validation_failed`, `verify_failed`, or
  `success`;
- every structured error code, location, offending key, and section slug;
- candidate character count and SHA-256 only — never raw candidate/source;
- timestamp.

Do not overload `usageHistory`; usage and diagnostics are related but distinct
concerns. Keep checkpoint parsing backward compatible when the new field is
absent.

Do not remove `priorCandidate` or `priorErrors`: completed invalid artifacts
still need that ephemeral state to build the next repair prompt. The new
append-only diagnostic history is additional persisted evidence, not a
replacement for the loop's next-attempt inputs. When an incomplete response
requires a fresh generation, clear/bypass those repair inputs for that attempt
without discarding the diagnostic history.

### 2. Make terminal reporting truthful

`repair_exhausted` and `batch status --json` must expose the ordered diagnostic
sequence or a deterministic summary of it. Never call the last attempt's error
count the total error count.

### 3. Separate incomplete generation from artifact repair

Recommended behavior for review:

- A provider-declared incomplete response (`stopReason === "incomplete"`, such
  as raw `abort`) is not a completed artifact and should not be fed back as a
  repair candidate by default.
- If another bounded attempt is available, issue a fresh stage-4 generation
  with the same authoritative closed list and source context, while retaining
  accounting and the prior incomplete diagnostic.
- A normally completed but structurally invalid candidate should continue to
  use the repair prompt with its exact validation errors.
- Keep token-limit (`length`) handling explicit; do not silently treat it as
  normal completion.

This behavior must remain provider-agnostic: branch on normalized semantics,
not on MiniMax or raw string `abort`.

### 4. Required regression tests

Cover at least:

1. `stop + invalid`, `stop + invalid`, `abort` — all three diagnostics persist.
2. `abort`, `stop + invalid`, `abort` — ordered history persists.
3. An incomplete response causes a fresh generation prompt on the next bounded
   attempt, with no prior partial candidate embedded.
4. A completed invalid response still causes a repair prompt with the exact
   structured errors.
5. `repair_exhausted` reports the full attempt sequence and correct counts.
6. Existing checkpoints without diagnostic history still load.
7. Usage accounting remains monotonic and exactly reconciled.
8. Key-leak regression remains green; diagnostics cannot retain secrets or raw
   prompt/candidate content.
