# Qualitative audit script for clean v16 artifact

This page documents the standalone Node script that statically audits the frozen clean v16 artifact for the concrete regressions observed in clean v7.

## When to use this page

- **Run** `node _qualitative-audit.mjs <artifactRoot>` to re-evaluate the artifact without invoking the paid pipeline.
- **Inspect** `metrics/qualitative-audit.json` to see the per-check pass/fail status and any failed pages.
- **Diagnose** a failing check by reading the `failedPageChecks`, `missingMmdLinks`, `duplicateDiagramDeclarations`, `commandsContradiction`, or `truncatedEndings` arrays.
- **Extend** the audit by adding new checks next to the existing ones in this single-file script.

## How it fits

This module lives at `docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v16/_qualitative-audit.mjs`, alongside the clean v16 rerun artifact. It reads only the frozen `livewiki/` and writes only into `metrics/qualitative-audit.json`, so it is independent of the paid generation pipeline. The script composes a small set of helpers into a series of independent structural and semantic checks; the helpers are described in the sections below.

## File discovery

<!-- lw:anchors docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v16/_qualitative-audit.mjs#walk -->

The `walk` helper enumerates files under a directory tree, optionally filtered by suffix. Its signature is:

```js
function walk(dir, suffix)
```

Given an existing `dir`, `walk` recursively descends into subdirectories and collects file paths whose names end with `suffix` when `suffix` is provided, or every file path otherwise. If `dir` does not exist it returns an empty array. Results are sorted before being returned, so callers see a stable order across runs. In this script `walk(wikiRoot, ".md")` supplies the markdown page set, and `walk(wikiRoot, ".mmd")` later supplies the Mermaid diagram set used for duplicate-declaration detection.

## Masking manual blocks and code regions

<!-- lw:anchors docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v16/_qualitative-audit.mjs#maskManualAndCode -->

The `maskManualAndCode` helper blanks out regions of a page that must not influence structural assertions, so the audit only inspects prose that was generated by the pipeline. Its signature is:

```js
function maskManualAndCode(text)
```

The function performs three passes. First, any HTML-comment block beginning with `lw:manual` and ending with `/lw:manual` is replaced with runs of spaces matching the original length, so byte offsets are preserved for later scans. Second, fenced code blocks (delimited by three or more backticks or tildes at the start of a line, with matching closers of equal length) are reduced to empty lines while still tracking whether a fence was left open. Third, the function scans the remaining text character by character; when it sees a run of backticks it looks for a matching run of the same width and, if found, replaces the whole span with spaces; otherwise it leaves the opening run in place so that `hasUnclosedInlineCode` can detect it. The function returns `{ masked, unclosedFence }`. The excerpt does not establish behavior for inputs containing both manual blocks and overlapping code fences simultaneously.

## Unclosed Markdown detection

<!-- lw:anchors docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v16/_qualitative-audit.mjs#hasUnclosedInlineCode -->

The `hasUnclosedInlineCode` helper is a thin wrapper that flags pages whose Markdown is not fully closed. Its signature is:

```js
function hasUnclosedInlineCode(text)
```

It delegates to `maskManualAndCode` and returns `true` when either `unclosedFence` is set or any backtick character survives in the masked output. It is used both inside `scanModulePage` to populate `unclosedMarkdown` on every page report and at the top level to decide whether a page is recorded in `truncatedEndings` with reason `unclosed_markdown`. A `true` result short-circuits the empty-body check for that page because an unclosed span already disqualifies the page.

## Per-page structural checks

<!-- lw:anchors docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v16/_qualitative-audit.mjs#scanModulePage -->

The `scanModulePage` helper produces a single per-page report object consumed by the overall gate. Its signature is:

```js
function scanModulePage(file)
```

For a given `file`, it reads the page text and parses the YAML frontmatter between `---` fences, extracting every entry under the `anchors:` list into `fmKeys`. It then walks the body for every HTML-comment marker beginning with `lw:anchors` and ending with `-->`, collecting keys into `sectionKeys`. For each marker it computes the visible prose between the marker and the next marker or heading, applies `maskManualAndCode` to that slice, strips blank lines and lines that are only an HTML comment, and records the marker's offset in `emptySections` when no visible prose remains. The report object returned by `scanModulePage` contains:

- `file` — the page path relative to `wikiRoot` with forward slashes.
- `frontmatterCount` and `sectionCount` — sizes of the deduplicated, sorted frontmatter and section key sets.
- `independentCoverageEqual` — whether the two sorted sets compare equal by JSON serialization, enforcing the rule that frontmatter and section markers must each independently cover the closed list.
- `frontmatterDuplicates` and `sectionDuplicates` — any keys that appear more than once within their respective collection.
- `emptySections` — marker offsets whose body had no visible prose.
- `unclosedMarkdown` — the result of `hasUnclosedInlineCode` on the full page text.
- `visibleSentinel` — a regex check for the literal `[untrusted /lw:... control marker omitted]` style sentinel that should not appear in generated output.
- `todoOrTbdProse` — a case-insensitive word-boundary check for `TODO` or `TBD` in the masked text, so any prose placeholder fails the gate.

A page is considered failed when `independentCoverageEqual` is false, any duplicate list is non-empty, `emptySections` is non-empty, `unclosedMarkdown` is true, `visibleSentinel` matches, or `todoOrTbdProse` matches.

## Top-level composition

The driver block at the bottom of the file combines the helpers into the final report. It selects module pages by filtering out `quickstart.md` and `architecture/overview.md` from the markdown list, runs `scanModulePage` over each, and gathers additional cross-file signals:

- `missingMmdLinks` parses Mermaid links in `architecture/overview.md` and flags any whose target file does not exist on disk.
- `quickstartUsesImportantSymbols` and `quickstartUsesKeyConcepts` check the headings of `quickstart.md`, with the check `quickstartUsesImportantSymbolsHeading` requiring the former and forbidding the latter.
- `benchmarkHelpersInImportantSymbols` scans the `## Important symbols` body of `quickstart.md` for fixture, test, and benchmark-helper paths so they cannot be promoted as product symbols.
- `duplicateDiagramDeclarations` walks every `.mmd` file and reports any `class` or node declarations that appear twice.
- `commandsContradiction` scans `commands.md` for lines that claim the module calls `process.exit(...)` while no same-line denial is present.
- `truncatedEndings` records pages where `hasUnclosedInlineCode` is true (reason `unclosed_markdown`) or where the body after frontmatter contains no non-empty line (reason `empty_body`).

These checks feed a `checks` object; `overallGate` is `"PASS"` only when every entry is truthy. The serialized object is written to `metrics/qualitative-audit.json` and also printed to stdout.
