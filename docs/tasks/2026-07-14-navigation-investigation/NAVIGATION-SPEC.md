**Status:** investigation deliverable for technical-lead review; not yet the
frozen implementation contract  
**Date:** 2026-07-14  
**Investigated revision:** `c30258c77306806f81665e71ad96348ec8f6c24e`

Preconditions were verified before investigation: `HEAD` and `origin/main`
both resolved to the investigated revision, and the tracked tree was clean.

## Scope and product boundary

This specification defines navigation improvements to the Markdown corpus
generated by livewiki. It does not propose a viewer, sidebar, search UI, or
other Phase 7 presentation work. It preserves the product's agent-first model:
anchors, search, and the closed symbol inventory remain the primary retrieval
mechanism for agents, while the same corpus becomes substantially easier for a
human to enter and traverse.

The following constraints are non-negotiable:

- Symbol keys remain `relative/path.ext#SymbolName`. No key or anchor format
  changes are proposed.
- `Module.id` remains the stable machine identity used by task targets, page
  paths, overview fragments, diagrams, graph edges, checkpoints, and exact
  partition validation.
- The exact-partition and exactly-once frontmatter/section-marker rules remain
  unchanged. Navigation prose never substitutes for anchor coverage.
- Navigation sections contain no `lw:anchors` markers unless they genuinely
  document closed-list keys. The expected design is that they contain none.
- Deterministic output is preferred whenever indexed facts, existing page
  metadata, or import edges suffice. This lot must not add a paid LLM call.
- `owner: human`, `owner: mixed`, and `lw:manual` preservation rules continue
  to apply to every automated rewrite.
- All generated prose continues to use the configured wiki language. Stable
  IDs, paths, keys, commands, and tool names are not translated.

## 1. Reader model

### 1.1 Agent answering “how does X work?”

**Intent.** Retrieve a small, trustworthy implementation slice, follow it to
specific code, and avoid loading the whole repository.

**Entry and path today.** The agent enters through the MCP
`livewiki_quickstart`, then normally uses `livewiki_search` and
`livewiki_read`. The current quickstart does not explain that route. Instead it
opens with repository counts and three machine-named modules:

> “This repository has **77 files** indexed and **427 symbols** extracted,
> organized into **13 modules**.”
>
> “- [core-src-02](architecture/overview.md#core-src-02) — 7 files, 80
> symbols”

— `docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v18/livewiki/quickstart.md:3-9`

The underlying module pages are strong retrieval targets. For example, a page
ties implementation prose directly to exact keys:

> “## Server”
>
> “<!-- lw:anchors packages/mcp/src/server.ts#createServer -->”
>
> “`createServer` is the only public entry point of the MCP module.”

— `docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v18/livewiki/mcp-src.md:43-49`

**Ideal path.** `livewiki_quickstart` explains the three-tool retrieval loop in
place: search for the concern, read the best page, then follow its exact anchors
to code. The agent needs no new page type to answer “how does X work?” and must
not be forced through human narrative first. From a module page it can return
to Quickstart, Tasks, or Architecture in one link.

### 1.2 Human onboarding to the repository

**Intent.** Understand what the repository is, identify its major concerns,
learn the safe first workflow, and know where to go next.

**Entry and path today.** The current quickstart gives counts, three numbered
module links, and ten symbols from one large file:

> “## Important symbols”
>
> “- `packages/core/src/batch.ts#accumulateUsage` (function)”
> “- `packages/core/src/batch.ts#aggregateTotals` (function)”
> “- `packages/core/src/batch.ts#attemptStage4Generation` (function)”

— `docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v18/livewiki/quickstart.md:11-16`

This is an index fragment, not an onboarding path. By contrast, OpenWiki states
the product promise and the intended use of the entry point before presenting
detail:

> “**living repository documentation** — markdown wiki, versioned inside the
> repo, anchored to code symbols, detectable-as-stale without spending an LLM
> token, and consumable by humans or any agent.”
>
> “This page is the entrypoint for agents and humans working on the
> **livewiki** codebase. Start here, then follow the section links to learn the
> architecture, workflows, integrations, and operational rules.”

— `docs/benchmarks/2026-07-10-minimax-m3/raw/openwiki/quickstart.md:3-5`

**Ideal path.** Quickstart gives a one-paragraph orientation, three concrete
product workflows, and two deliberate onward choices: Tasks for “I need to do
something” and Architecture for “I need to understand the shape.” A human can
reach any product module in no more than two internal links.

### 1.3 Human performing a repository task

**Intent.** Complete a change or operation such as adding a provider, running
the batch, or fixing a failed verification without first reverse-engineering
the directory partition.

**Entry and path today.** A reader must infer that `llm.md`, `commands.md`, or a
numbered `core-src-*` page contains the task. The pages themselves open in
implementation order. `commands.md`, for example, starts with the command
registration internals:

> “## batch command (Phase 3)”
>
> “`registerBatch` attaches the `livewiki batch` command to a Commander
> program. It dispatches among four subcommands...”

— `docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v18/livewiki/commands.md:34-43`

OpenWiki demonstrates the useful alternative: task verbs are first-class
navigation labels, and a page opens by telling the reader how to use it:

> “## Adding an LLM provider”
>
> “1. New adapter? Add `packages/core/src/llm/<provider>.ts` implementing the
> `LlmClient` interface...”
>
> “3. New **preset** without a new adapter? Add a row to `PRESET_TABLE` in
> `presets.ts` — **data only, no code**.”

— `docs/benchmarks/2026-07-10-minimax-m3/raw/openwiki/operations/development-workflow.md:26-33`

**Ideal path.** Quickstart links to a deterministic Tasks page. Tasks groups
verb-led task cues extracted from accepted module-page openings and links each
cue to its module page. The module page repeats its task context before the
anchored reference detail. Task readers can therefore choose by intent without
changing the machine partition.

## 2. Corpus evidence

### 2.1 What livewiki already does well

The v18 architecture overview is a dependable inventory hub. It declares that
it is deterministic, groups modules by repository role, and links only to
artifacts that exist:

> “Diagrams in this section are deterministic (regenerated by `livewiki init`
> / `index`); the module pages they link to are written by the batch
> (`livewiki init --batch`) or manually.”
>
> “Modules are grouped by repository role and ordered by prioritization within
> each group. Each module links to artifacts that exist on disk.”

— `docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v18/livewiki/architecture/overview.md:10-12`

It also keeps auxiliary coverage visible without presenting it as product code:

> “## Test fixtures”
>
> “### sample-ts-repo-src”
>
> “## Tooling and benchmarks”
>
> “### tools”

— `docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v18/livewiki/architecture/overview.md:70-90`

These properties must survive Lot L. Exhaustive coverage is not the navigation
problem; presentation and routes through that coverage are.

### 2.2 Why the current corpus feels implementation-shaped

The primary hub presents machine IDs, counts, and links but no responsibility
or task cue:

>

— `docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v18/livewiki/architecture/overview.md:24-26`

The module page repeats the ID as its title and then spends its visible opening
on the complete anchor inventory:

> “title: core-src-03”
>
> “anchors:”
> “  - packages/core/src/imports.ts#collectImports”
> “  - packages/core/src/imports.ts#extractImportsFromTree”

— `docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v18/livewiki/core-src-03.md:2-6`

After frontmatter, it opens directly with implementation:

> “## Import extraction (tree-sitter)”
>
> “`extractImportsFromTree(tree, lang)` walks a parsed tree-sitter `Tree` and

— `docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v18/livewiki/core-src-03.md:82-87`

The problem is not that this material exists. It is valuable reference
material. The problem is that no human-purpose layer precedes it.

OpenWiki organizes entry routes by concern rather than directory. Its

> “### Architecture”
> “- [Three-layer architecture and package map](architecture/overview.md)”
>
> “### Workflows”

Topic pages explain when the concern matters before enumerating mechanics:

> “The batch pipeline is **not** the heart of the product — incremental mode
> is. But batch is what you reach for when you have an undocumented (or freshly
> cloned) repo and need a complete wiki before you start iterating.”

— `docs/benchmarks/2026-07-10-minimax-m3/raw/openwiki/workflows/batch-pipeline.md:3-5`

They also end with related routes rather than dead-ending:

> “## Where to go next”
>
> “- [Indexing and anchor-ledger](indexing-and-debt.md) — what powers stages 1

— `docs/benchmarks/2026-07-10-minimax-m3/raw/openwiki/workflows/batch-pipeline.md:165-169`

The pattern to borrow is orientation, task labels, and editorial cross-linking.
The generated operational facts themselves are not authoritative and must not
replace livewiki's verified anchors.

### 2.4 What not to copy from OpenWiki

OpenWiki's quickstart includes volatile project status and test totals:

> “## Phase status (snapshot from AGENTS.md)”
>
> “Total test count at last green run: **430 passed + 8 skipped** across core,
> cli, mcp.”

— `docs/benchmarks/2026-07-10-minimax-m3/raw/openwiki/quickstart.md:37-49`

Those facts can age independently of source structure. The target quickstart
must be a short operational entry point built from livewiki's own stable
commands and current indexed facts, not a generated project-status essay.

OpenWiki also demonstrates that polished navigation does not guarantee precise
behavioral coverage. Its MCP page states only the normal verification flow:

> “If any `error`-level issue touches the page ... the file is **rolled back**
> (`unlink` best-effort) and the tool returns an `isError` result with details.”

— `docs/benchmarks/2026-07-10-minimax-m3/raw/openwiki/integrations/mcp-server.md:41-50`

The v18 livewiki page makes the same omission while describing the same normal
path:

> “`livewiki_write_doc` additionally runs `verify` against the repo and rolls
> the file back when an error-level issue is reported against the just-written
> page.”

— `docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v18/livewiki/mcp-src.md:43-49`

Navigation work therefore needs a factual-precision rider; it must not trade
traceability for editorial smoothness.

## 3. Findings and required design by question

### Q1 — Reader model

Lot L must serve all three readers without forcing them through the same route:

| Reader | Required entry point | Required path |
|---|---|---|
| Agent asking how X works | `livewiki_quickstart`, search, or direct MCP search | Quickstart explains search → read → anchored code; direct search remains valid |
| Human onboarding | `livewiki/quickstart.md` | Quickstart → Tasks or Architecture → module page |
| Human doing a task | `livewiki/quickstart.md` or `livewiki/tasks.md` | Task cue → module page opening → anchored reference sections |

The agent path stays shortest. Human routes are additive navigation over the
same verified pages, not a separate narrative corpus.

### Q2 — Quickstart target

The target quickstart is **DETERMINISTIC**. It is generated in `init.ts`, works
without provider configuration, and is regenerated after batch completion. It
does not use `buildQuickstartPrompt` and does not add a paid call.

Required outline, in this order:

1. `# Quickstart`
2. A one-paragraph explanation that this directory is the repository's living,
   anchored wiki and that Quickstart is the low-token entry point.
3. `## Choose a path`
   - **Understand the repository** → `architecture/overview.md`
   - **Do a repository task** → `tasks.md`
4. `## Document a repo`
   - `livewiki init` for deterministic scaffolding/indexing.
   - `livewiki init --batch` for full module documentation.
   - One link at most to the relevant deeper page when that page exists.
5. `## Query the wiki from an agent`
   - `livewiki_quickstart` → `livewiki_search` → `livewiki_read`.
   - Explain that anchors identify the source surface; do not dump a top-symbol
     list here.
6. `## Pay documentation debt`
   - Discover with `livewiki_debt` or `livewiki status --json`.
   - Write with `livewiki_write_doc` or direct edit.
   - Resolve only after `livewiki verify` is clean.
7. `## Repository facts`
   - Current deterministic counts: files, symbols, modules.
   - No raw ranked symbol list and no top-three numbered module list.

The page should remain low-token: at most 100 nonblank lines and 700 English
words in the deterministic English fixture. This is intentionally much shorter
than copying OpenWiki's phase history, complete command catalog, and project
status, while still answering the three core workflows directly.

### Q3 — Module-page opening and cross-links

The stage-4 page content is **PROMPT** work in `prompts.ts`. Presence of the
required opening is a **DETERMINISTIC** structural artifact check so a provider
cannot silently omit it. Both the initial and repair prompts carry the same
contract.

After required frontmatter and before the first anchored implementation
section, every generated module page must contain:

```markdown
# <human-meaningful title>

<One sentence: what responsibility this page covers.>

## When to use this page

- <Verb-led task cue.>
- <Verb-led task cue.>

## How it fits

<One short paragraph naming the module's role and its immediate repository
context. No claim of a complete call graph.>
```

Rules for the opening:

- It contains two to four task bullets, each beginning with an action verb.
- It contains no `lw:anchors` marker. Closed keys remain distributed exactly
  once among the later reference sections that document them.
- It does not repeat the full path inventory, symbol table, or frontmatter
  anchors in prose.
- It does not claim that the module is an “entry point” merely because it has
  many symbols.
- Fixtures, tooling, benchmarks, and docs use honest task context (“Use this
  page when maintaining the benchmark harness”), not product prominence.

Every generated or mixed module page must also end with a **DETERMINISTIC**
`## Navigate` block containing:

- Quickstart.
- Tasks.
- Architecture overview.
- Up to three related module pages selected from direct import-graph neighbors,
  preferring product-role modules and then existing prioritization order.

The related links are assembled from exact known page paths and emitted only
when the target exists. The block contains no anchors and no LLM-authored path.
The deterministic writer must preserve every manual block byte-for-byte and
must not rewrite `owner: human` pages.

### Q4 — Corpus-level hub structure

`architecture/overview.md` is doing the job of a mechanically reliable
**inventory hub**, but not the whole job of a human navigation hub. Its current
entries provide only ID, counts, and artifact links. Lot L should preserve its
role grouping, exact HTML IDs, existence checks, diagrams, and auxiliary-module
separation while improving each module card to show:

- Human display title first.
- Stable ID second, explicitly labeled “module ID”.
- File and symbol counts.
- Up to three representative paths, selected deterministically.
- Existing page/class-diagram links only.
- Direct dependency/dependent neighbors, using human display titles.

The missing layer between Quickstart and module pages is a task index.

#### New page: `livewiki/tasks.md`

- **Classification:** DETERMINISTIC.
- **Owner:** `owner: generated`.
- **Generation:** `init.ts` assembles it without a new LLM call. Before stage 4,
  it uses deterministic module display-title fallbacks. After stage 4, it is
  regenerated from each accepted module page's `When to use this page` bullets
  plus module role and stable path.
- **Organization:** Product tasks first; then separate Fixture, Tooling and
  benchmark, and Documentation-maintenance sections. A product module appears
  exactly once as a task group. Auxiliary modules never appear in the primary
  product task list.
- **Links:** Every task cue links to its module page only if that page exists.
  A failed/missing page remains listed as unavailable text, not a dead link.
- **Anchors:** No code anchors and no `lw:anchors` markers. It is navigation,
  not a substitute for source coverage.
- **Verify:** Repository-wide `verify` checks its internal Markdown links like
  any other page. It has no closed-list obligation and does not change the
  stage-4 exact-coverage calculation. It is included in the manifest snapshot.

This page is deterministic assembly over already accepted artifacts. It may
reuse task-cue text; it must not summarize, reinterpret, or invent behavior.

### Q5 — Human-meaningful module titles without identity changes

Names such as `core-src-03` are acceptable machine identities and unacceptable
primary human labels. The v18 corpus makes that distinction visible because the
same string is the overview heading, page path, and frontmatter title.

Lot L must introduce a presentation-only `displayTitle` channel:

1. **DETERMINISTIC heuristic fallback.** Derive a readable label from the
   shortest unique directory context and split ordinal, for example “Core
   source — part 3 of 5”, never merely `core-src-03`.
2. **PROMPT semantic title.** Stage 4 must emit a concise responsibility title,
   for example “Module planning, import resolution, and init output”, from the
   supplied symbols/source. It must not use the stable ID alone as the title.
3. **Optional stage-2 presentation refinement.** Stage 2 may return a title
   independently of `id`. Missing, malformed, duplicate, or low-quality titles
   degrade to the deterministic fallback and do not reject an otherwise exact
   path partition.
4. **Post-stage-4 display.** Overview and Tasks use the accepted page
   frontmatter title when present, otherwise the deterministic fallback.

`displayTitle` has no role in:

- Page filename (`livewiki/<module.id>.md`).
- Overview HTML fragment (`#<module.id>`).
- Batch task target/checkpoint.
- Diagram filename or graph node identity.
- Exact-partition validation.
- Symbol keys, frontmatter anchor values, or section markers.

The stage-2 exact-partition validator continues to validate paths and machine
IDs exactly as today. A presentation-title failure can never drop, duplicate,
merge, or reassign a path.

### Q6 — Prompt/deterministic/post-MVP split

The operative rule is: semantic explanation belongs to stage 4; navigation
assembled from known paths, roles, titles, and edges is deterministic; visual
presentation belongs to Phase 7.

- **PROMPT:** human semantic title, one-sentence responsibility, “When to use
  this page”, “How it fits”, literal-signature discipline, and visible
  non-happy-path coverage.
- **DETERMINISTIC:** Quickstart template, Tasks assembly, display-title fallback,
  overview cards, related-module selection, link existence checks, and the
  per-page Navigate block.
- **POST-MVP:** hiding frontmatter, persistent sidebar/tree, breadcrumbs rendered
  by a site, client-side task filters, full-text UI, and responsive layout.

No recommendation depends on MiniMax, OpenWiki, the benchmark repository, or a
specific Markdown renderer.

### Q7 — Factual-precision rider

Yes: stage 4 should require a literal signature for a function-behavior claim,
but once per primary function in the section rather than before every sentence.
The exact rule is:

> When a section asserts behavior of a named function or method and the symbols
> table supplies a non-empty signature, copy that signature byte-for-byte from
> the symbols table into inline code or a fenced code block in the same section
> before the behavioral explanation. Do not reconstruct, normalize, shorten, or
> “improve” it. One literal signature covers subsequent claims about that symbol
> within the section. If the table has no signature, do not invent one; limit
> the prose to facts visible in the supplied source and identify the symbol by
> its exact closed-list key.

The need is concrete. v18 says:

> “`refinePeerDirectoryFragmentationError(...)` takes a candidate
> `ExactPartitionError` and refines its message...”

— `docs/benchmarks/2026-07-10-minimax-m3/rerun-clean-v18/livewiki/core-src-03.md:199-212`

OpenWiki shows that literal signatures are readable and compact when presented
directly:

> “interface LlmClient {”
> “  readonly provider: LlmProvider;”
> “  readonly model: string;”
> “  generate(req: GenerateRequest): Promise<GenerateResult>;”
> “}”

— `docs/benchmarks/2026-07-10-minimax-m3/raw/openwiki/integrations/llm-providers.md:28-48`

A signature does not prove branch behavior, so the prompt must add this
companion rule:

> When the supplied source visibly contains a material `throw`, `catch`,
> fallback, rollback, early return, or fail-open/fail-closed branch for the
> documented symbol, describe that branch or explicitly scope the prose to the
> normal path. Never use “always”, “guarantees”, “mandatory”, or equivalent
> absolute language while omitting a visible exception. If the relevant source
> is truncated, say that the excerpt does not establish exhaustive behavior.

**Validator implication:** none for this lot. Do not add a semantic or
signature-quotation validator. Exact prose matching would be brittle across
languages and Markdown forms, while signature presence still cannot prove
branch completeness. Add prompt unit tests for the exact rule and output-shape
fixtures that demonstrate compliant signatures; leave `verify`, closed-list
validation, and marker accounting unchanged.

### Q8 — Acceptance model

Navigation quality is accepted through structural and route checks, not an
unscored reviewer impression. The full criteria are in Section 5.

## 5. Checkable acceptance criteria for the implementation lot

### 5.1 Preconditions and deterministic behavior

1. `livewiki init` with no provider configuration and no API key generates
   `quickstart.md`, `tasks.md`, and `architecture/overview.md`; no LLM client is
   constructed and no network call is made.
2. Re-running init on unchanged indexed input produces byte-identical
   navigation content except already-established manifest timestamp semantics.
3. Shuffling the input file/module order does not change module IDs, display
   titles, task ordering, related-module selection, or navigation links.
4. Batch call count is unchanged by Lot L: the navigation layer adds zero paid
   calls. Usage accounting remains exact and monotonic.

### 5.2 Quickstart

5. Quickstart contains the exact headings `Document a repo`, `Query the wiki
   from an agent`, and `Pay documentation debt` in that order.
6. Each of the three sections contains an executable command/tool sequence and
   requires no more than one internal link to reach deeper detail.
7. Quickstart links directly to `tasks.md` and
   `architecture/overview.md`; both targets exist in a successful init.
8. Quickstart contains no “Top entry points” ranking, no raw top-symbol list,
   and no project phase/test-count snapshot.
9. The deterministic English fixture is at most 100 nonblank lines and 700
   words. MCP `livewiki_quickstart` continues to return this file unchanged.

### 5.3 Task index and corpus routes

10. `tasks.md` has `owner: generated`, has no frontmatter `anchors:` list and no
    `lw:anchors` marker, and is included in the manifest snapshot.
11. Every product module appears exactly once as a task group. Fixture,
    tooling/benchmark, and documentation modules appear only in their separate
    secondary sections.
12. Every emitted task link targets an existing module page. A missing/failed
    page produces labeled unavailable text, never a broken link.
13. Starting at Quickstart, every existing product module page is reachable in
    at most two internal links through Tasks or Architecture.
14. From every generated module page, Quickstart, Tasks, and Architecture are
    each reachable in one link.
15. Related-module links are limited to existing direct import neighbors, are
    capped at three, and are deterministic under input reordering.

### 5.4 Module-page contract

16. After frontmatter, every newly generated product and auxiliary module page
    begins with H1 display title, one responsibility sentence, `When to use this
    page`, two to four verb-led task bullets, and `How it fits`, before the first
    anchored implementation section.
17. Navigation/opening sections contain no `lw:anchors` markers. Every closed
    key still appears exactly once in frontmatter and exactly once across the
    later section markers.
18. In the implementation fixture, no product page's accepted frontmatter title
    equals its stable `Module.id`. Pre-batch fallback titles remain readable and
    explicitly label split ordinals.
19. Page filename, overview HTML ID, task target, graph identity, diagram path,
    and checkpoint target remain derived from `Module.id`, never display title.
20. Regenerating `owner: mixed` pages preserves all `lw:manual` blocks
    byte-for-byte and retains `owner: mixed`. `owner: human` pages are not
    modified to add an opening or Navigate block.

### 5.5 Factual precision

21. Prompt unit tests assert the literal-signature rule, the no-invention
    fallback for empty signatures, and the material-exception-branch rule in
    both initial and repair prompts.
22. A stage-4 fixture containing a non-empty symbol-table signature emits that
    exact signature byte-for-byte before behavior prose.
23. A stage-4 fixture with an empty signature does not fabricate one.
24. A fixture source containing a normal path plus a material catch/fallback
    produces scoped prose that mentions the branch; this remains a prompt/output
    fixture, not a new semantic validator.

### 5.6 Existing safety and quality gates

25. Existing exact-partition, unique-ID, closed-list, duplicate-anchor,
    empty-section, Markdown-closure, manual-block, rollback, and key-leak tests
    remain green without weakening assertions.
26. Repository-wide `livewiki verify` reports exit 0 and zero issues after init
    and after a complete batch. Internal links in Quickstart, Tasks, Overview,

## 6. Open questions for the maintainer

1. **Task-index path:** approve the recommended top-level
   `livewiki/tasks.md`, or prefer `livewiki/navigation/tasks.md`? Top-level is
   recommended because it is one link from the low-token entry point and does
   not imply a viewer hierarchy.
2. **Artifact enforcement:** should missing `When to use this page` / `How it
   fits` be a repairable artifact-validation error? Recommendation: yes, with a
   single structured error code, because prompt-only compliance will vary by
   provider.
3. **Stage-2 title field:** should optional stage-2 refinement be allowed to
   suggest `displayTitle`, or should semantic titles come only from stage 4?
   Recommendation: allow it but never rely on it; deterministic fallback is
   mandatory because `--no-refine` is a supported path.
4. **Related-module direction:** should the Navigate block include dependencies,
   dependents, or both? Recommendation: both, labeled separately when space
   permits, with a combined cap of three and product-role preference.
5. **Task-cue reuse:** is verbatim reuse of accepted `When to use this page`
   bullets in `tasks.md` acceptable, or should Tasks list only module titles?
   Recommendation: reuse verbatim; deterministic re-summarization is impossible
   and a new LLM call is unjustified.
6. **Quickstart installation detail:** should `Document a repo` include package
   installation/invocation syntax, or only commands after installation?
   Recommendation: keep install syntax out until distribution is frozen; show
   stable `livewiki` commands only.
7. **Page-title enforcement:** should the artifact validator reject a product
   page whose title exactly equals its stable ID? Recommendation: yes for
   product modules, but permit a deterministic fallback for failed/absent pages
   and keep auxiliary-page wording honest rather than artificially polished.
